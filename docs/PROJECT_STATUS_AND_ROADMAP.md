## 0. 一页结论（TL;DR，v1.4.0 基线）

**这个项目已经是一个“功能完整的演示级 TV 客户端”，但还不是“可持续迭代、可交付给真实用户”的工程。** 当前主要矛盾不是缺功能，而是：

1. **番剧/PGC 播放实际失败**，且根因不是 HANDOFF 里写的“CDN 403”，而是接口身份参数用错（实测可复现，修复成本低）。
2. **清晰度被锁死在 720P/360P**，接口其实能返回 DASH 1080P/4K，但播放内核 `MediaPlayer` 不支持 DASH。
3. **设置页三个开关是“假开关”**：弹幕/自动播放/优先高清都不生效、不持久化。
4. **失败路径不可用**：网络失败时展示 8 条伪造的“精选内容”、错误/空/未登录三态混同、无重试。
5. **工程基线缺失**：无 git、无测试、无 CI、Debug 签名、0 日志——本机原先连 Android SDK 都没有，构建不可复现。
6. **验收材料失真**：`design-qa.md` 宣称“无 P0/P1/P2、passed”，与同仓库 HANDOFF 的两组 P1 矛盾，且部分 QA 截图过期或只是旧图复制。

**继续开发的总思路：不要先加新页面，先花约 2 周做“v1.5 可信与稳定”，把播放、错误、设置、工程基线、文档五件事补齐；然后再按“播放内核（DASH/Media3）→ 产品补全（原生化/分页）→ 发布与架构”三个阶段推进。** 详见第 4 节。

## 2. 关键发现（按严重度）

> 完整清单见 3 份子系统报告（共 100+ 条，均带 `文件:行号` 与修复建议）。本节只保留影响决策的主干问题。

### 2.1 P0：无
三份审查均未发现必然崩溃/数据损坏路径。两个“P0 潜力项”需低端盒子实测：封面全尺寸解码 + 无字节预算缓存（`BiliRepository.java:33-38,443-467`）可能 OOM；搜索串行校验 + 线程池无取消可能造成长时间“假死”。

### 2.2 P1（影响核心场景/验收可信度，建议下一迭代必须处理）

#### P1-1 番剧/PGC 播放失败：根因是接口参数，不是 CDN
- 代码事实：`resolveBangumi()` 已经拿到 `epId`，但 `resolveArchive()`（`PlaybackRepository.java:132-159`）只用 `bvid`/`avid` + `cid` 请求 PGC 接口，**没有把 `ep_id` 传下去**；且 PGC 回退只在标准接口“抛异常”时触发，不校验 `result.code`。
- 本次实测：同一集（《葬送的芙莉莲》ep779775）：标准接口 `-404`；PGC 接口传 `bvid` → **`-400 请求错误`**；传 `avid`/`ep_id`/`season_id` → `code=0` 且有 `durl`。**当前代码在 bvid 非空的集数上必然失败**，这解释了 QA 截图中的“正在缓冲… → 播放失败”。
- 修复：PGC 分支改用 `ep_id`（首选）或 `avid`，并校验 `result.code`/`error_info`；同时补 `backup_url` 候选与错误文案。预估 **1.5–3 人日**（含重拍 QA 证据）。
- 旁证：`qa/implementation-search-bangumi-playback-v1.4-fixed*.png` 与旧图 **SHA-256 字节级相同**，不能作为“已修复”证据。

#### P1-2 清晰度上限 720P，DASH 能力未使用
- 代码事实：`platform=html5&fnval=1`，只解析 `durl[0]`，全工程无 `dash` 处理（`PlaybackRepository.java:136-159`）。
- 实测：该组合只返回 720P/360P；换 `platform=pc&fnval=16` 即返回 DASH（未登录可用轨道最高 480P，`accept_quality` 含 1080P+/4K，登录后能否解锁需实测）。**本轮实测中 playurl 不需要 WBI 签名即可拿到 DASH**，瓶颈在播放内核。
- 影响：这不仅是画质问题，也是 PGC/影视失败的结构性原因之一（仅提供 DASH 的内容无法播放）。
- 修复路径：决策门（见 4.3）→ 引入 Media3/ExoPlayer 解析 DASH 音视频分轨。

#### P1-3 设置页是“假开关”
- `MainActivity.java:73-75,329-333,546-551` 三个布尔值只改文字；无 `SharedPreferences`、无 Intent 传参、无配置类。
- `PlayerActivity` 恒为弹幕开、1×、`qn=80`（`PlayerActivity.java:38,45,104-108`；`PlaybackRepository.java:132-137`）；`settingAutoPlay` 全工程无消费方。
- 修复：定义语义 → `SharedPreferences` 持久化 → 传参给播放器 → 逐项验收。**0.5–1 人日**。

#### P1-4 登录态与凭据安全
- `APP_KEY`/`APP_SECRET` 明文硬编码（`BiliAuthRepository.java:41-42`）；Cookie 存在 `CookieManager`，无加密、无退出登录；`hasSession()` 只看字符串是否含 `SESSDATA=`（不校验有效性）。
- `android:allowBackup="true"` + Debug 构建 → Cookie 可被备份通道/`run-as` 提取（Debug 下 `run-as` 是确定的）。
- 登录轮询在 `onPause` 被移除、`onResume` 不重启（`LoginActivity.java:49-50`），切后台再回来扫码登录会停摆。
- 修复：`allowBackup=false`/备份规则、补退出登录、加 `nav` 接口校验会话、轮询恢复、凭据移出源码并补合规说明。**约 1 人日**。

#### P1-5 失败路径不可用：伪造兜底 + 无错误模型
- 推荐/热门/排行/分区/直播接口失败时返回 8 条**写死的伪造内容**（含假播放量、死链，`BiliRepository.java:505-516`），用户无法分辨故障与真实内容。
- 回调第二参数同时承载“错误”和“成功提示”；`getJson` 不校验 HTTP 状态/业务 `code`（`BiliRepository.java:469-485`），风控/未登录/删稿/网络失败全部退化成同一句话。
- 修复：删伪造数据 → 引入 `ApiError{kind,code}` → UI 区分 `LOADING/EMPTY/ERROR/LOGIN_REQUIRED` 并给“重试”。**2–3 人日**。

#### P1-6 搜索延迟放大器
- 搜索返回后对最多 28 条视频**串行**逐条请求 `view`（单次 9s+9s 超时，`BiliRepository.java:177-195`），弱网下可放大到分钟级；切分类会重复触发且不取消。
- 修复：只校验可见项、并发 ≤3、按 bvid 缓存校验结果、点击播放时兜底。**1–2 人日**。

#### P1-7 工程基线缺失 / 验收材料失真
- 无 git/`.gitignore`/测试/CI；release 未配置签名；0 处 `Log`；本机原先无 Android SDK，构建不可复现。
- `design-qa.md:58,85` 的“无 P0/P1/P2、passed”与 HANDOFF 的两组 P1 矛盾；账号相关页只在登出态验证；`qa/implementation-settings-native.png` 仍显示 1.3.0；`fixed` 失败截图与旧图字节相同。
- 修复：`git init` + 首次提交 + tag、最小 CI、lint/构建结果写回文档、QA 证据按版本归档。**1–1.5 人日**。

## 3. 架构判断：为什么“继续加功能”会越来越慢

1. **UI 是一个 570+ 行的自绘内部类**：`area/navIndex/filterIndex/gridIndex/firstRow/personalMode/pageRequestGeneration` 全部手工维护；新增页面 = 继续往 `MainActivity` 里加 `if/else` + 绘制代码 + 按键分支，回归成本随页面数线性上升。
2. **数据层是“一个 Repository 干所有事”**：传输、解析、回退、缓存、格式化混在 517 行里；解析与 `android.*`/网络 IO 强耦合，无法单元测试。
3. **“无 AndroidX、零依赖”是当前工程的最大优点，也是最大约束**：APK 只有 1.7MB、供应链风险极低；代价是 HTTP/缓存/图片/生命周期全部手写。**是否引入 Media3（必须打开 AndroidX）是一个需要你拍板的产品级决策**（见 4.3）。

建议的分层目标（不急，但在 v1.7 前逐步做）：

```text
ui/       页面状态机 + 绘制组件（可拆：NavBar/FilterRow/Grid/PlayerOverlay）
domain/   VideoItem(id, kind, ...) + 用例（刷新/分页/播放决策）
data/     NetClient + JsonParser（纯 Java 可测）+ 错误模型 + 缓存
player/  PlaybackResolver + 播放引擎（MediaPlayer 或 Media3，可切换）
```

## 4. 后续开发路线图

### 4.1 总原则

- **先“可信”后“丰富”**：先把失败路径、设置、工程基线做对，再谈新页面。
- **每阶段都能独立交付**：不追求一次大重构；用版本节奏切分，保证随时可回滚（前提是先有 git）。
- **用证据验收**：每项修复都必须有真机/模拟器截图或日志，QA 文档按版本归档，不再出现“fixed 图 = 旧图”的情况。
- **接口不稳定性是长期风险**：所有 B 站 Web 接口都是非公开接口，任何阶段都要保留“错误可诊断、可降级、可回退”的能力。

### 4.2 v1.5「可信与稳定」（建议优先，约 8–12 人日 / 1–2 周）

| # | 任务 | 关键动作 | 人日 | 验收标准 |
| --- | --- | --- | --- | --- |
| 1 | 工程基线 | `git init` + `.gitignore` + 首次提交 + `v1.4.0` tag；GitHub Actions 跑 `assembleDebug lintDebug` | 0.5–1 | 任何改动可回滚；CI 绿 |
| 2 | **PGC 修复** | PGC 分支传 `ep_id`/`avid`、校验 `result.code`、`backup_url` 候选、错误分类 | 1.5–3 | 抽 5 部不同类型番剧/影视，能播或给出明确原因；重拍 QA |
| 3 | 错误模型 + 删伪造 | `ApiError`、`LOADING/EMPTY/ERROR/LOGIN_REQUIRED`、重试键 | 2–3 | 断网/风控/未登录三态可区分；不再出现假内容 |
| 4 | 设置打通 | 偏好持久化 + Intent 传参 + 播放器读取；明确“自动播放/优先高清”语义 | 0.5–1 | 关闭弹幕/改清晰度后重进播放器仍生效 |
| 5 | 搜索改造 | 可见项优先、并发 ≤3、bvid 缓存、取消；412 风控回退体验 | 1–2 | 弱网搜索 < 10s 出首屏；切分类不叠加耗时 |
| 6 | 生命周期/线程 | 单例执行器 + `close()` + 请求取消；播放器 `onPause`/音频焦点/状态保存 | 1–2 | 反复进出播放页线程数不增长；后台不再出声 |
| 7 | 登录/安全 | `allowBackup=false`、退出登录、会话校验、轮询恢复 | 1 | 换账号/退出可用；登录后切后台再回来仍能完成扫码 |
| 8 | 文档纠偏 | README/design-qa/HANDOFF 与代码对齐；QA 按版本归档 | 0.5 | “视觉 QA ≠ 功能验收”写清楚；不再有 1.3.0 旧图当现状 |

**v1.5 完成后的项目状态**：能稳定演示、能给别人装、出问题能定位、改代码不怕丢——这是继续开发的地基。

### 4.3 v1.6「播放体验」（约 6–10 人日 / 2–3 周）

**先做决策门（0.5–1 天）**：完成 v1.5 的 PGC 修复后，抓包/Logcat 确认剩余失败是否只出现在“仅 DASH/302/CDN”场景：

- 若剩余样本都能用渐进流稳定播放 → Media3 可暂缓，只做“720P 上限”提示。
- 若失败集中在 DASH/高清/重定向 → 启动 Media3 迁移（**需要 `android.useAndroidX=true`**）。

| 步骤 | 内容 | 人日 |
| --- | --- | --- |
| 1 | 打开 AndroidX + 引入 Media3（exoplayer/dash/hls），普通视频/控制层回归 | 2.5–4 |
| 2 | DASH：`platform=pc&fnval=16` → `dash.video[]/audio[]` 分轨组装，清晰度用 `TrackSelector` 无缝切换 | 2–3.5 |

| 4 | 番剧体验：选集/下一集、播放进度记忆、错误码文案（会员/地区/版权/试看） | 1.5–2.5 |
| 5 | 回退开关：保留 MediaPlayer 引擎一版，按设备/配置切换 | 0.5–1 |

### 4.4 v1.7「产品补全」（约 8–12 人日 / 2–3 周）

### 4.6 需要你先拍板的 4 个决策

1. **发布形态**：纯自用 / 小范围内测 / 上架？——决定安全与合规投入的优先级。
2. **是否接受引入 AndroidX/Media3**？——决定能否上 1080P/4K、DASH、HLS 直播，以及 APK 体积是否可接受。
